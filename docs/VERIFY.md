# Verify the gate you installed

Recusal's whole argument is that the thing which produces work must not be the thing
that certifies it. That argument applies to Recusal's own artifacts. This page is how
you check them yourself, without trusting this repository's word for anything.

Every command below was run by hand against a published release before it was written
down, and [`.github/workflows/verify-release.yml`](../.github/workflows/verify-release.yml)
exists to run all of them, negative controls included, against any published version on
demand. See [Evidence](#evidence) for exactly which of those has happened so far.

Substitute the version you installed for `0.7.1` throughout.

| Question | Answer |
|---|---|
| Was this file built by this project's release pipeline? | GitHub build provenance, below |
| Was this file signed at the release boundary? | Sigstore bundle, below |
| Is what PyPI serves the same file? | byte comparison plus PEP 740 provenance, below |
| What was in the build? | SBOM, below, with its honest retention boundary |

## 1. Build provenance: which workflow built this

Download the artifacts from the [GitHub Release](https://github.com/philpaz/recusal/releases),
then ask GitHub who built them:

```bash
gh attestation verify recusal-0.7.1-py3-none-any.whl --repo philpaz/recusal \
  --signer-workflow philpaz/recusal/.github/workflows/build-dist.yml
```

Exit 0 means the artifact carries a provenance attestation naming this project's
*reusable builder* workflow. `--signer-workflow` is the part that matters. Without it
the check accepts any workflow in the repository; with it, the attestation must name
the one workflow whose only job is to build and attest, which is GitHub's documented
path to SLSA Build Level 3.

Confirm the check can fail, before you believe it when it passes:

```bash
gh attestation verify recusal-0.7.1-py3-none-any.whl --repo philpaz/recusal \
  --signer-workflow philpaz/recusal/.github/workflows/not-the-builder.yml
# Error: verifying with issuer "sigstore.dev"   (exit 1)
```

## 2. Signatures: the release-boundary Sigstore bundles

Each release attaches a `.sigstore.json` bundle next to each distribution. The bundle
carries the certificate and the signature, so verification needs the bundle and the
file, nothing else:

```bash
pip install sigstore

python -m sigstore verify github --offline \
  --bundle recusal-0.7.1-py3-none-any.whl.sigstore.json \
  --cert-identity "https://github.com/philpaz/recusal/.github/workflows/release.yml@refs/tags/v0.7.1" \
  --repository philpaz/recusal \
  recusal-0.7.1-py3-none-any.whl
# OK: recusal-0.7.1-py3-none-any.whl
```

The certificate identity is the workflow that *signed*, `release.yml` at the release
tag, which is not the workflow that *built*. Signing happens at the release boundary
and building happens in the reusable builder, so the two identities differ on purpose.
Section 4 explains why both are worth checking.

The negative control, again worth running once:

```bash
python -m sigstore verify github --offline \
  --bundle recusal-0.7.1-py3-none-any.whl.sigstore.json \
  --cert-identity "https://github.com/philpaz/recusal/.github/workflows/build-dist.yml@refs/tags/v0.7.1" \
  --repository philpaz/recusal \
  recusal-0.7.1-py3-none-any.whl
# fails: the identity did not sign this   (exit 1)
```

`--offline` verifies against the trust root shipped with the Sigstore client rather
than refreshing TUF metadata over the network. That is the honest mode for a bundle
that already carries its own material, and it is stated here because it is a real
difference: an offline run will not learn about a trust-root rotation. Drop `--offline`
to check against freshly fetched metadata.

## 3. PyPI: same bytes, and PyPI's own provenance

`pip install recusal` does not fetch the GitHub Release, so verify that PyPI serves
the same file:

```bash
python - <<'PY'
import hashlib, json, urllib.request
meta = json.load(urllib.request.urlopen("https://pypi.org/pypi/recusal/0.7.1/json"))
for entry in meta["urls"]:
    local = hashlib.sha256(open(entry["filename"], "rb").read()).hexdigest()
    print(entry["filename"], "MATCH" if local == entry["digests"]["sha256"] else "DIFFERS")
PY
```

PyPI also holds its own [PEP 740](https://peps.python.org/pep-0740/) attestation for
each file, generated by the publishing step:

```bash
curl -s https://pypi.org/integrity/recusal/0.7.1/recusal-0.7.1-py3-none-any.whl/provenance | \
  python -c "import json,sys; b=json.load(sys.stdin)['attestation_bundles'][0]['publisher']; print(b)"
# {'kind': 'GitHub', 'repository': 'philpaz/recusal', 'workflow': 'release.yml', ...}
```

## 4. The two attestation layers, stated exactly

Do not conflate these, and do not accept a summary that does:

- **PyPI PEP 740 provenance** names `release.yml`, the workflow that published. It
  answers "did this project's release workflow put this file on PyPI".
- **GitHub build provenance** names `build-dist.yml`, the reusable workflow that
  built and attested. It answers "did this project's dedicated builder produce these
  bytes".

Both are true at once, and they answer different questions. A verification that checks
only the first would accept an artifact that a different job in the repository had
built.

## 5. The SBOM

Each build catalogs the distributions as an SPDX SBOM. It is a **workflow run
artifact**, not a release asset, which means it is downloadable from the release run
in the Actions tab and it expires with GitHub's artifact retention window. That is a
real limitation and it is stated rather than papered over: if you need a durable SBOM
for a specific version, download it while the run artifact still exists, or open an
issue and it will be attached to releases going forward.

## What none of this establishes

- **Not byte-reproducibility.** Provenance says which workflow produced these bytes.
  It does not let you rebuild them and get the same bytes. This project has never
  claimed reproducible builds.
- **Not correctness or safety of the source.** An attestation binds an artifact to a
  build. It does not read the code. The reasons to trust what the code *does* are the
  tests, [`SECURITY.md`](../SECURITY.md), and [`PROVEN.md`](PROVEN.md), not this page.
- **Not your deployment.** Verifying the artifact says nothing about who can write to
  your `settings.json` or which interpreter your hook runs. That boundary is
  [`SECURITY.md`](../SECURITY.md).

## Evidence

Every command on this page was run by hand against **v0.7.1** on 2026-07-27, with both
negative controls confirmed failing: a signer workflow that never built the artifact,
and a certificate identity that never signed it.

[`verify-release.yml`](../.github/workflows/verify-release.yml) has **not yet been
exercised on a published version**. A `workflow_dispatch` workflow only becomes runnable
once it is on the default branch, so its first run happens after this document ships.
That distinction is the point of this page: a procedure is proven by a run, not by
existing.
